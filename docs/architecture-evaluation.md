# 架構評估與驗證順序

## 現況判斷

本專案同時包含三種不同性質的需求：

1. **營運系統**：庫存、批號、效期、訂藥、到貨。
2. **採購情報**：三同藥品比價、非藥品低價試賣雷達。
3. **會計系統**：採購費用、應付帳款與付款。

不建議由單一客製網站一次重做全部能力。

## 建議邊界

| 系統 | 主要責任 | 暫不負責 |
|---|---|---|
| Odoo Inventory + Purchase | 商品、供應商、庫存、批號、效期、補貨、採購單、到貨 | 三同辨識、全網低價雷達 |
| 採購情報模組 | 中盤商報價、單位成本、三同比較、試賣候選 | 庫存帳與正式會計 |
| GnuCash | 會計科目、付款、帳務報表 | 即時庫存與效期 |
| Sites 原型 | 流程與操作介面驗證 | 直接讀取本機資料 |

## 為什麼雲端網站看不到本機資料

架在外部網域的網站無法自行讀取藥局電腦中的 Excel、SQLite、GnuCash 或其他資料庫。可行的資料交換方式只有：

- 使用者主動上傳 CSV／Excel。
- 本機同步程式主動推送資料。
- 本機系統提供受保護的 API。
- 將主要資料搬到雲端資料庫。
- 把整套系統部署在藥局內網。

因此，在確認既有庫存來源之前，不應先把 Sites 當成正式庫存主系統。

## Odoo 驗證範圍

第一階段只安裝或啟用必要模組：

- Inventory
- Purchase
- Contacts／Vendors

以測試資料完成以下案例：

1. 建立一個商品與兩個供應商報價。
2. 設定採購包裝單位與庫存單位換算。
3. 設定最低／最高庫存。
4. 產生補貨建議或詢價單。
5. 建立採購單。
6. 登記部分到貨。
7. 到貨時輸入批號與效期。
8. 查詢近效期商品。
9. 匯出已驗收採購資料。

完成後才判斷 Odoo 是否過度複雜，以及需要客製哪些畫面。

## 第一階段不做

- 不自動登入或爬取中盤商網站。
- 不直接讀寫 GnuCash 原始資料檔。
- 不做 Odoo 與 GnuCash 雙向同步。
- 不匯入真實病患或處方資料。
- 不把 API 金鑰、供應商帳密或真實藥價提交到 GitHub。
- 不先建立完整的三同藥品 AI 自動辨識。

## 採購情報與 Odoo 的銜接

兩套採購情報系統維持獨立資料邏輯，但共用一個最小交接格式：

| 欄位 | 用途 |
|---|---|
| source_type | drug-comparison 或 retail-deal-radar |
| source_reference | 原始報價或頁面識別 |
| vendor | 供應商 |
| source_product_name | 原始品名 |
| matched_product_id | 對應的 Odoo 商品，可暫時空白 |
| package_spec | 採購包裝 |
| order_quantity | 建議採購量 |
| quoted_price | 原始報價 |
| unit_cost | 換算單位成本 |
| quoted_at | 報價時間 |

使用者確認後，候選項目才轉成 Odoo 的詢價單或採購單。

## GnuCash 銜接原則

- 只輸出已驗收或已確認的採購資料。
- 初期採 CSV 單向匯出，由使用者在 GnuCash 確認後匯入。
- 不讓網站直接修改 `.gnucash` 檔。
- 若未來全面採用 Odoo Accounting，再評估停止重複維護 GnuCash。

## 待確認問題

1. 現有庫存資料目前存在藥局 POS／管理系統、Excel，還是沒有電子資料？
2. 訂藥主要透過中盤商網站、LINE、電話、傳真，還是混合使用？
3. 是否需要管理所有商品批號與效期，或只管理特定品類？
4. 哪些電腦需要同時操作？是否都在同一個藥局內網？
5. GnuCash 目前實際記錄到哪個細度：每張進貨單、每個供應商，還是只有彙總金額？

## 決策門檻

只有在 Odoo 測試流程出現以下任一狀況時，才考慮自建庫存核心：

- 日常操作步驟明顯過多，無法透過設定或簡化畫面改善。
- 藥品主檔與三同關係無法合理擴充。
- 現有藥局系統無法與 Odoo 交換必要資料。
- 自架與維護成本高於客製輕量系統。
